## 4. 全项目能力梳理

### 4.1 网站与业务

原黑金主站、图鉴、聊天、测验、抽卡收藏、商品和沙箱订单继续保留。新增证据面板使用局部适配脚本；视频工作台仅新增移动端适配 CSS。本次审查没有操作前端文件。

重要边界：主站完整 React 原始工程仍未恢复；现有 React/TypeScript 草稿并不等于所有正式页面均由可维护源码重建。不要在简历里说“独立从零实现完整 React 全站”来描述目前的源码归档。

### 4.2 自动知识建设

`source_acquisition.py` 实现有界官方 API 获取、作品白名单、固定修订、上游哈希及渲染哈希、段落提取、繁简检索、缓存、dry-run、幂等入库和回放。原文保持原字形，检索规范化文本不替代引用原文。

实际主链路来自维基文库。Wikidata 是身份候选适配器，真实批次曾受 maxlag 阻塞；HF/Kaggle/GitHub 资料大部分仅调查或隔离。不能写“已融合 Kaggle、HF、Wikidata 等多源大规模知识库”。

### 4.3 证据政策与版本治理

`evidence_policy.py` 将机器核对原文与专家批准分开。机器轨道校验页面版本、段落偏移、引用文本、哈希、许可、权限、来源健康状态及实体候选，输出 MACHINE_VERIFIED。关系为 MENTIONS，语义支持仍 UNVERIFIED。

其价值是可追溯和不夸大，并非自动判定历史真伪。工作体裁/白名单也只是工程路由策略，不是历史学权威分类器。

### 4.4 检索与问答

`KnowledgeRepository + EvidenceSearch + AnswerService` 对接旧聊天、V2 搜索、图鉴证据、Research 工具与创作工程。已具备稳定实体 ID、别名/繁简、BM25、历史/文学范围、基础多实体与指代、精确原文跳转和失效拒用。

目前常规回答以原文摘录和来源归属为主，`generation_mode=RETRIEVAL_ONLY`、`model=None`。这与“检索后由通用大模型组织自然语言解释”不同；后者尚未接到统一证据主链路。不要在演示中用零模型调用暗示大模型能力特别高效。

### 4.5 Research Agent

真实工具包括实体检索、证据检索、版本读取、来源比较、证据边检查、覆盖检查和受控获取。可演示“无证据→发现目标章节→获取/读取真实快照→机器核对→入库→重新检索”。

已具备工具白名单、调用/时间/页数/网络请求限制、日志哈希和缓存标记。当前是确定性工具型 Agent/workflow，不能叫已验证的 LLM 多 Agent 智能协商。可把“受控 Agent 工具链”作为工程贡献。

### 4.6 可恢复内容生产

已有数据库持久化 Job/Node、DAG 依赖、重试、取消、租约/fencing、检查点、产物校验与 FFmpeg CPU 合成，仓库测试涵盖进程中断/恢复和局部重算。机器引用已可进入带来源提示的视频。

这不是本地文生视频模型，不需要 GPU。视频工厂是可信知识的下游应用，而不是本轮继续扩张的主方向。

### 4.7 测试与安全

88 项记录覆盖许多正确性边界，包括假引文、错误偏移/版本/实体、私密来源、失效、重复入库、资源隔离及原媒体流程。不能从这些测试推出“没有任何安全漏洞”或“历史回答已达专家水平”。GitHub Actions 当前未发现运行记录；可复现的独立运行仍需完成。

## 5. 本次已完成的两个小范围修复

### F1. 证据类问题被文化推荐抢先响应

旧 `culture_reply` 对“讲故事/性格/聊聊/周边”先识别文化或商品意图，只有少量词触发事实分支。“给我讲故事，但先列原文”“介绍性格，史籍如何记载”等可能进入无引用的文化回答。

修复：集中定义 `_EVIDENCE_INTENT`，补原文、引文、文献、史籍、记载、证据以及相应繁体形式，明确证据请求优先；普通故事、趣味匹配、预算商品流程不变。这是规则路由修复，不是完整意图模型。

### F2. ResearchAgent 异常路径没有释放 provider

旧 `run` 只在成功走到尾部时关闭 HTTP provider；检索、解析、数据库或预算异常可绕过清理。

修复：`run` 通过 `try/finally` 包装 `_run`，无论成功或异常均关闭 provider 并清空引用；关闭失败记录不含源文/凭据的错误类型，不吞掉原任务异常或丢弃正常结果。

验证：`scripts/verify_resume_hardening.py`；证据 `reports/resume-readiness/targeted-validation.json`。两文件本地测试使用的字节内容与提交后的 Git blob 匹配。**完整应用回归待本地执行后才能合并。**

## 6. 仍需优先解决的具体问题

### P0：来源新鲜度会影响简历演示

当前机器引文要求来源健康检查时间在七天内，但没有后台刷新服务。固定版本原文虽仍在库里，七天后可能整批退出可引用集合；某次网络失败也可能降为 UNAVAILABLE。演示时不能依赖“之前统计有 81 条”。

先实现启动前健康报告、有限批次刷新和明确的离线快照演示。区分临时网络错误、证据内容不一致、许可/权限收紧和实际撤回；后两者必须保持严格禁止，不能为了演示取消校验。离线模式须显示快照日期、网络不可用与新鲜度，不伪装为实时核对。

### P0：新 clone 不是一键可演示环境

runtime 数据库、缓存和截图被忽略；当前启动需要本机指针和原运行库。仅有源码与 source manifest 不代表离线能重建全部记录。需要在全新目录测试空库初始化、固定来源回放和小型演示资产构造；不带用户账号/密钥/私有媒体，不擅自上传整库。

### P0：检索预算内的反证可能被挤掉（静态代码风险，待复现）

当前 EvidenceSearch 先填满 limit，之后才用 `if len(hits) >= limit: break` 加入同 proposition 反证，因此反证补充可能在最需要时无空间。多实体代表性阶段还可能超过小 limit。需在候选规划阶段保留配额，确保明确的 SUPPORTED/CONTRADICTS 对照不被普通相似结果全部挤掉；新增饱和 Top-k 和多实体小预算测试，不可通过放大 Top-k 冒充修复。

### P0：正式简历必须区分提及与回答

原文确实出现某马名，不等于确认其身份、主人、年代或问题全部前提。当前机器答案主要展示原文，不能称复杂推理完成。界面要先回答“本次能支持什么/不能支持什么”，再展示原文与来源；可用确定性归属模板，不能依赖未经授权的 LLM。

### P1：实际可用的生成能力尚未接通

需要自然语言综合时可在统一 AnswerService 后添加可选 Provider，但默认关闭网络/收费路径；只有已有明确授权才运行。没有凭据不能把整轮工作标失败，也不能测试通过后写“真实模型已验证”。本次两天内的简历收尾不必强行加入此能力。

### P1：覆盖率和关系模型尚有限

继续自动化发现有意义的原文，但不为追求 100/100 放宽实体匹配、许可和来源政策。优先少数旗舰案例的多个来源、互文关系和不同体裁展示；复杂事件时间、多跳与自动语义矛盾尚未充分实现。

### P1：检索性能需以规模变化验证

每请求重建全知识快照、读取原文记录并核验文档，当前小规模尚可，扩大数据会增加数据库/解析/哈希开销。先测冷/热路径、实际中位/高分位、数据量和错误率，再用 revision-keyed 缓存优化；权限/许可/撤回变化必须立即失效。不要立即换成新向量数据库。

### P1：对外材料与主分支未同步

main 仍停留在旧任务文档，原 README 与第三方说明含 49 项测试、三条 DRAFT 等历史描述。必须清楚标历史/最新，PR 合并后固定一个 release candidate commit；公开仓库/部署仍需另行授权。旧报告原样保留，不抹去时间线。
