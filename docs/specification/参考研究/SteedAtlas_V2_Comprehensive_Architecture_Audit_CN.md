## 0. 执行摘要与判定

**总体结论：有条件通过，须修订后才能作为工程实施依据。** 报告最值得保留的研究主线是“断言级证据溯源与成本高昂、非确定性多模态任务的安全增量恢复”。最重要的改正是：（1）将自研调度器降级为待比较选项；（2）明确缺少供应商幂等能力时不能实现严格的 exactly-once 提交；（3）修复“认识论标签、审核状态、版本号”混用；（4）增加版本化强缓存基线，避免创新性来自故意削弱的对照组；（5）补充间接语义依赖与人工核验；（6）区分科研内核与产品开源复用；（7）把研究用模拟、真实媒体验收及网站上线三条路线分别管理。

## 1. §1 Executive synthesis：研究定位

**[通过]** 报告明确将“历史证据到媒体产物的溯源链 + 增量恢复机制”视作研究核心，而不是基础视频模型本身；并主动指出最强对照是普通哈希缓存，结果可能无改进。这种可证伪的表述值得保留。两位判断型 Agent 加大量确定性工具的方向合理，有助于减少协调错误。

**[需改]** “模块化单体 + 自有数据库持久调度器”为默认推荐，依据不足。研究核心未必需要掌控每一种租约、通知和消费确认实现。应将 A1（现有 FastAPI 加可靠 Worker）、A2（成熟执行框架加自有证据/恢复决策）并列，用相同故障集实测决策。模仿专业工作流平台不能自动推出学术创新。

**[落地]** 产品名“百骑谱”与研究代号“SteedAtlas”明确分离，避免将面向公众的中文产品强制改名；主线是精致文化产品和可靠的 AI 系统并存。

## 2. §2 Scope / method / evidence conventions：研究边界

**[通过]** 不接触私有仓库、未运行代码、未发付费请求；A-D 证据等级与“概念设计、经验支持、未知”成熟度标签科学。直接保留。

**[需改]** 报告从公开镜像读取 Pixelle README 后将其全部列 C 过于笼统：GitHub 项目搬迁或更名后，应优先核对当前官方仓库、LICENSE、NOTICE 和标记的 commit SHA。发布日期、GitHub 星标和 README 功能声明不能证明生产可靠性。

**[落地]** 后续本地代码审计结果应写成独立证据附录，不修改 Claude 原来的“纯公共资料研究”事实声明。源码审计也只能证明“有此实现”，不能证明线上运行状态。

## 3. §3 Literature / prior art：文献审查

**[通过]** Temporal、LangGraph、Sagas、Build Systems à la Carte、Nextflow、Dagster、W3C PROV、C2PA、BEIR、RRF、ALCE、FActScore、MAST、FrugalGPT、VBench、间接提示注入等研究背景总体有针对性。

**[需改]** 不能简单说“这些机制都已有但组合存在空白”。应补增量视图维护（incremental view maintenance）、构建系统的细粒度依赖、数据流血缘、版本化/非单调知识管理、物化视图失效、非确定性任务重试以及语义依赖近似等方向。需要找出真正最接近 R3 的系统与明确差异，否则相关工作不充分。

**[需改]** 引用准确性、年份和会议等级逐条核实；标准规范说明“能表达什么”，不能被当作“性能提高证明”。MAST 不能直接推导“两个 Agent 最优”，它仅提供谨慎选用多 Agent 的经验理由。

**[落地]** 为每条重要主张建立一张 Claim/Evidence/Limitations 表；至少标注原始文献、适用条件、工程推断、是否直接适用于多模态历史视频。

## 4. §4 Architecture alternatives：架构方案比选

**[通过]** 反对把现有系统完全交给通用视频平台；选择模块化单体对少量文化条目和有限并发是合理起点。

**[重大修改]** 15%、12% 等权重来自设计者主观偏好而非用户需求与测量结果。把“自主可控”同时算作科研独特性和检查透明度，会让自研方案被重复加分；反之忽略了维护租约、事务 outbox、对账的实现与验证成本。应做敏感性分析：不同权重下排名是否稳定，并将运行时开发工时、故障恢复正确性列为硬门槛。

**[重大修改]** “自研运行时只硬化一轮，不通过便改用 Temporal”不是足够稳健的工程决策。切换编排引擎会改变时序、接口和运营模型，不能仅靠抽象接口就保证成本低。先做薄原型 A2 与 A1 的失效验证，再决定方向。

**[落地]** 以 POC 测试驱动最终架构；将一套稳定证据图、TaskNode、Artifact 与工具适配协议作为框架无关的核心。

## 5. §5 Target architecture：容器、序列、失败恢复

**[通过]** API 服务、角色、知识、Agent、Runtime、Worker、外部媒体模型分层清楚；外部模型输出必须按不可信内容校验；人类审批与预算作为代码约束，原则正确。

**[需改]** C4 Level 1 的简化图没有提供完整操作流，不应被当成部署网络图。数据库及 Worker 共享对象存储时还需明确读写权限、对象可见性、签名 URL、传输安全和审计；“只有 Service 写 DB”若 Worker 的状态更新都经 Service，需明确是 HTTP 命令还是事务服务，并解释一致性边界。

**[重大修改]** §5.5 在 `SUBMITTING` 后崩溃、尚未获得供应商 task ID 的情形，没有普遍可靠的查重办法。没有幂等键/可查询客户端引用时，系统必须进入 `UNKNOWN_OUTCOME`、暂停自动重发并人工处理。不能承诺任意 provider 的严格一次提交。

**[需改]** 取消时存储迟到回调应遵守保留期限和资源成本，不能默认保留所有巨大媒体资产；同时考虑重复、乱序、签名失败、任务已删除的事件。

## 6. §6 Conceptual contracts and data model：数据模型与正确性

**[通过]** `Source / Passage / Claim / EvidenceRef / TaskNode / Attempt / Artifact / ProviderCallback / ReviewDecision / CostLedger` 的方向合理；追踪模型、工具版本、产物哈希和审批记录是必要的。

**[重大修改：内部概念冲突]** §6.1 分别定义 `Claim.epistemic_status`（包括 `DISPUTED`）和 `Claim.review_state`（`PROPOSED / APPROVED / RETIRED`）。但 §9.1 称“状态从 APPROVED 变为 DISPUTED”，把两个不同维度混成一个字段。必须明确：任何 `epistemic_status`、证据关联、有效期、review_state 改动是否会强制递增不可变版本，并把该版本纳入有效性判断；对已批准但存在争议的内容，策略应取决于所选“仅史实/允许文学”范围，而非一刀切阻止。

**[重大修改：租约竞态]** `lease_owner` 单字段 CAS 容易在租约过期和重新分配时产生陈旧写入/ABA 风险。每次分配需生成递增 `fencing_token` 或原子代次，提交结果时检验 node、attempt、lease_epoch 和数据版本；需要事务隔离及唯一索引配合。

**[重大修改：幂等]** `H(job_id, fingerprint, attempt-policy-generation)` 只是客户端去重标识，不代表第三方会去重。应增加 ProviderCapability（支持幂等键、查询 client_ref、状态可查询性、撤销和费用语义），对无法确认任务状态者禁止静默重发。

**[需改：数据生命周期]** 内容寻址的 Artifact ID 不适合直接绑定用户授权；同一字节内容跨用户复用须同时满足所有权、来源、媒体许可、隔离域和保留策略。应区分 `content_hash`、`artifact_id` 和 ACL。临时下载 URL 不能作为长期 `storage_uri`；存储需要不可变版本或保留失败证明。

**[需改：费用不变量]** `reserve + actual <= cap` 若未说明实际费用结算时释放 reservation，易重复计算。需定义预算状态机：估价→预留→实际结算/释放→退款或冲销，并处理不明费用、并发场景和价格币种精度。

**[需改：边语义]** `SUPPORTS`, `CITES`, `REALIZES`, `PROMPTS`, `GENERATED`, `USED` 的边方向和类型需要统一；需要完整上游和下游索引、语义版本、循环检测。PROV-O 是交换映射，不一定适合作内部执行图结构。

## 7. §7 Knowledge, retrieval, provenance：可信知识系统

**[通过]** 100 份左右领域数据上先做别名表和 BM25、Dense/Hybrid 通过实测决定是正确的；明确“史料支持 ≠ 客观真相”，避免文献与小说混用。为断言标注 `ATTTESTED`、文学、传说和创作等类别比简单一个 source 标签有用。**注意正式拼写应统一 `ATTESTED`。**

**[需改]** 领域知识的最小单位应该先人工校验出处及引文位置；自动拆分 100 份资料并贴事实标签不能视作完成证据系统。文档可能包含历史类比、间接引文和一文多说；单一 `A-D` 来源评级不足以取代断言级支持审查。

**[需改]** 对“只用 APPROVED + MODERATE 以上强度回答”的强制规则，需按不同问题和创作模式分级，否则对文学传说查询可能过度拒答。事实查询、文学内容解读与创作模式需采用不同的透明表述。

**[需改]** 语义/结构关系跨段及别名多跳的问题不等于必须引入知识图数据库；优先使用关系型表、索引、人工核验。发布端应显示精确段落与版本，并明确“文学作品记载”不是“历史证实”。

**[落地]** 先选 3 份不同来源性质的名马精品资料做完整证据链样例，其余逐步扩展；建立引用准确率、拒答准确率、人审一致性三类指标。

## 8. §8 Agent Runtime reliability：长任务、恢复与成本

**[通过]** 抛弃长期付费流程对 FastAPI `BackgroundTasks` 的依赖是正确的。Worker、任务表、超时、状态机、签名回调、取消、预算与可观测性设计方向合理。

**[重大修改]** `At-least-once` 投递不能推出 `exactly-once` 外部执行。任务提交写库前/写库后两种崩溃窗口必须区别对待。对返回任务 ID 前失败但不支持查询的媒体服务，应暂停并呈现不确定状态，而不是自动 retries。

**[重大修改]** 固定 `retry budget` 需要 ProviderError 类别。429、5xx 也不总是未计费；有的媒体服务在响应超时前已经生成，重新提交将产生双份费用。应把“幂等能力矩阵”作为接入条件。

**[需改]** Callback 签名不一定由供应商支持；不能假设“全部 signed callbacks”。无可验证 webhook 的服务宜主动轮询/使用受信中转；回调验签、重放窗口、任务所有权和迟到事件要分别保证。

**[需改]** 运行时需要心跳失败时的协调，租约代次原子更新，状态机不变量测试与灾难恢复演练；成本账本需要同时统计 API 费用、重试支出、人工审核工作时长和本地 GPU 计算。

**[源码差距]** 原百骑谱 `app/routers/workflow.py` 创建或重跑任务时通过 `background_tasks.add_task(run_site_workflow_task, task.id)` 启动；重跑还会重置 `node_states` 和 `result_payload`。现状并非持久任务运行时。

## 9. §9 Research hypotheses and novelty：科研核心严格审查

**[通过]** H1/H2/H3、HB1/HB2、负面假设和标准化基线体系很合格。敢于说明“R3 可能不如 R2”是报告最重要的学术优点。

**[重大修改：最强基线不足]** R2 描述为仅依赖内容哈希，R3 加入 Claim 状态。如果 R2 没有把知识状态当成依赖，R3 的优势部分来自人为削弱对照。新增 R2+：常规但完整的依赖图 + 知识版本 + 审核状态 + 精细缓存；再比较 R3 是否真正节省成本或提高准确性。

**[重大修改：状态模型]** 当前形式化的 `valid(v)` 只检查 claim 是否 APPROVED、版本匹配和产物存在，并没有充分处理“仍然 APPROVED，但从史籍改为有争议的文学叙述”或编辑了同一版本的元数据。把 epistemic 状态、权限范围、Claim 审批、证据集合版本纳入 validity，而不只是 `status(c)`。

**[重大修改：最小性宣称]** `R(Δ)=Reach(...)` 在静态、完全依赖图的前提下是一个保守重算闭包，并不自动是最小重算；动态依赖、同值早截断、跨镜头风格/人物一致性、共享旁白与合成全局依赖可造成过/漏失效。应把“最小安全重算”改为可量化目标，并证明或测量保守性与错漏率。

**[需改：因果设计]** H1 降低重复付费调用，与 H2 避免不安全复用是不同轴的目标；不能为了节省钱而把正确性置于次级。主要比较应先设 `unsafe_reuse=0（模拟已知真值场景）` 的正确性约束，再比较成本、耗时和人工审核负担。

**[需改：H3]** 质量感知重试依赖视频接受概率预测模型，真实数据不足时极易被过拟合。先将 R4 标记探索性，暂不作为第一篇论文主线。HB2 的“知识标签能否改变观众认知”是人机交互研究，需分离于系统论文，不要同时扩展太广。

**[落地]** 两条主线：Track A（可靠恢复）优先，Track B（证据支持）辅助；先找强基线，若无有效增益就如实报告负面结果或转向可复现的工程性能研究。

**[通过]** 将视频系统、模型、框架视作可换模块，而不直接整库包裹，方向合理；MIT/Apache/BSD 的许可证风险及 GPL/模型权重独立授权的区分也是合理提醒。

| HunyuanVideo / MiniMax H3 | 待许可证复核 | 若有地域限制，以官方权重 License 与实际使用地域为准；不能根据研究档案的推断地理位置直接判定不可用 |

**[重大修改]** 0-100 集成评分是人为加权的设计判断，不是测试成绩，不应在简历或答辩中当成独立测量结果。应再附具体兼容性试验、真实环境、版本/Commit、安装体积与依赖冲突数据。

**[官方复核]** PySceneDetect 官方说明主要是镜头剪辑边界检测；LTX2.5 的官方模型卡确实描述 $10M 收入阈值，但商用/微调许可需看原文。来源见文末。

## 11. §11 Security, governance, IP：真实系统优先级

**[通过]** 外部返回值和检索内容不可信，发布/删除/付费受代码和人类审批约束，审计记录独立存储，密钥与用户信息不进入公开轨迹，要求合理。

**[必须补充]** SSRF：用户输入的 Webhook URL、媒体 URL、参考素材 URL 在后端请求时可能触达内部网络；统一域名白名单、DNS/IP 解析重检、跳转控制。Webhook/下载不能简单根据 `http/https` 就判断安全。还需测试路径穿越、跨用户对象引用、RAG 文件写入权限、富文本 XSS、上传内容类型伪造及生成媒体是否意外公开。

**[源码已见]** `/api/v1/ai/build` 在自身路由中未添加登录/管理员权限，接受 `out_path` 并可写入指定输出文件；`PUT /rag-library/{horse_id}` 只依赖当前登录用户，不见角色授权。`config.py` 提供开发默认 JWT secret/DEBUG。若公网未受额外保护，这些必须 P0 解决；仅凭代码尚不能证明生产站存在同等暴露面。

**[需改]** “所有角色变化强制第二审”对个人/小团队可能不可行，可用角色隔离、双人审查作为公开发布模式要求，但本地演示可由明确批准的 operator 兼任并留审计轨迹。

**[需改]** 素材版权审查不能只放最终 G2 发布前，还应在输入素材进入系统时记录限制、在模型调用前检查是否允许上传第三方服务；按权利范围限制日志保存和公开演示。

## 12. §12 Product and accessibility：精致化路线

**[通过]** 文化数字博物馆 + AI 创作工作台的双模式；知识引用可点击、历史/文学标签透明显示；同一 Runtime 在 Guided/Expert 两种视图呈现；关注 WCAG 2.2 AA，方向都正确。

**[需改]** 现有主站保存了编译后的 React 产物，完整 React/TS 工程并不齐；“只用一套设计系统”在产品概念上成立，落地前必须先寻找源工程或重建可维护 UI。不能直接在压缩产物上进行大量改造。部分旧工作流 CSS 设有 `min-width:1120px`，移动端需求并非改几个 token 可达。

**[需改]** 统一设计不等于绝对统一视觉：文化页可使用有辨识度的编辑型字体和温和底色；工作台维持高对比、低干扰的信息密度。重要的是导航、控件、状态和品牌一致。

**[需改]** “所有核心目录页无 JavaScript 可用”涉及服务器渲染或静态化，成本大；应将公共展示页 SEO/首屏作为优先条件，创作工作台以可访问性和可用性为主。

**[落地]** 第一批三种完整用户旅程：名马档案→证据问答→视频创作；失败任务→局部恢复；创作完成→质量和来源报告。先完成真实业务，再优化动效。

## 13. §13 Reproducible evaluation：实验与统计审查

**[通过]** 三类结果（知识可信、运行可靠、媒体体验）不合并成单一评分；模拟→故障注入→小额真实供应商→用户研究的分层方案科学；对照、消融、盲评、负面结果都值得保留。

**[需改：数据集]** “7 类每类约30条”约210题是起始标注预算，不是统计学充分性的证据；实体层划分与仅三匹旗舰之间样本不足，需更多独立实体或明确只做小样本可行性研究。检索测试若提示词、别名表使用测试实体信息，需明确哪些属于合法词典而非数据泄漏。

**[需改：故障注入]** 30 个随机种子/每个单元可能造成大量相似伪随机任务，且 0 次重复并不能证明真实环境零重复。需结合重要故障的确定性可达性测试、状态机模型检查、属性测试、多进程竞争测试及置信区间；只做 30 seeds 不足以验证绝对性质。

**[重大修改：评测定义]** `unsafe_reuse = invalid reused artifacts / reused artifacts` 若某方案始终不复用，就会因分母0而被错误解读为优；应同时报告不安全复用**绝对数量/受影响机会数量**和覆盖率、拒绝重用率、额外误失效次数。`wasted spend / total` 要明确失败重试为何算浪费还是必要代价，并把外部费用与本地计算分开。

**[需改：统计]** McNemar / Wilcoxon 等检验只是建议，数据有任务/实体/种子分层相关性，未必满足独立样本假设。事先选主终点、效应量、配对设计和多重检验控制；为零事件指标提供置信上界，而非只报零。

**[需改：评审]** LLM 作审稿人存在风格偏差和模型自评偏差；评估“历史真实性”需依据标注过的来源，不只是 NLI 判断；知识支持、历史真假、观众理解是三个不同变量。

**[工具精度]** PySceneDetect 可用于镜头切换检测，但冻结帧时长、静音比例、字幕同步等应由专用媒体分析工具实现，不能用“使用 PySceneDetect”一笔带过。

## 14. §14 Five-minute demonstration：展示计划

**[通过]** 一条名马档案到视频成片的端到端故事贯穿 RAG、Agent、故障恢复与证据报告，比五个孤立界面更适合答辩。明确标记 simulated provider、预生成素材、真实执行逻辑是重要学术诚信要求。

**[需改]** 五分钟中再生成 3 个真实高质量片段不可控，Demo 最好展示预生成素材 + 在线运行故障模拟 + 可重复的对账/失效逻辑。每个镜头角标区分“实时执行”“预生成”“模拟计费”“实测计费”。

**[落地]** 增加展示“批改一个史料后，正确性为何优于 R2+”的小型对照画面，否则评委看到的只是普通缓存命中。

## 16. §16 Uncertainty register：前置条件与阶段验收

**[通过]** U1-R3 是否明显超越 R2、U3-外部供应商重试/计费语义、U8-素材权利、U12-标注一致性等是关键未知项，排序大体合理。

**[重大修改]** “V1 必须回答 U2/U3/U8/U12 才允许任何实施；V2 必须回答 U1 才决定 Runtime”过于绝对。P0 安全修复、测试框架、前端恢复、离线模拟原型不依赖供应商 API 或 100 条史料完成清洗，应先行推进。U1 需要构建小型模拟器和两套版本才可测试，因此不能作为“允许实现任何东西”的前置条件。

**[需改]** 按研究—工程两个并行门制定：工程门 E0（安全、可复现启动、测试）；研究门 R0（可实现的模拟 DAG、受控 3 例证据集、强基线）。R0 验证后才决定是否投资完整自研 Runtime 和大规模数据标注。真实付费任务必须明确授权与预算上限。

## 19. 应锁定的关键修订（按优先级）

**P0：安全与正确性前置**

1. 防护知识库写入、路径输入和生产默认密钥；修正权限与文件读取访问。外部 URL 下载和 Webhook 全面 SSRF 安全检查。
2. 定义 `Claim` 不可变版本、认识论状态、审核状态、引用证据集合与权限策略，全部版本化。
3. 定义真实供应商幂等能力与 `UNKNOWN_OUTCOME`，不得宣称普适一次性收费提交。
4. 定义租约 `fencing_token`、任务唯一键与预算预留/结算两套原子规则。

**P1：核心架构试验**

5. 建立少量有人工批准的精细史料与 `Passage→Claim→Sentence→Beat→Clip` 实例，验证正确率和标注成本。
6. 定义强基线 R2+，单独测量 R3 相比它的好处与代价。
7. 两种 Runtime POC：薄自研与成熟框架，加同一模拟媒体端，同一故障注入套件。
8. 从旧工作流迁移 DAG 结构、接口和状态机；存储内容哈希与完整依赖。
9. 生成器/审核器角色克制，拿“单 Agent + 工具”作为不可缺少的对照。

**P2：产品与媒体**

10. 复用现有 FFmpeg/Providers；仅在提升成片质量时引入 Pixelle/MoneyPrinterTurbo 的适用模块。
11. 重建可维护的 React 前端、两种工作台视图和统一品牌；内容主页优先精品化。
12. 引入基础解码、时长、音量、字幕和镜头检查；素材版权及史料状态在发布前核查。

**P3：科研成果**

13. 完成实际样本与模拟故障的消融、效应量、置信区间与负面结果分析。
14. 公开有授权的模拟器、任务样本、实验配置与分离来源的成果报告；私有仓库、未授权媒体和密钥不公开。

## 20. 修改后的核心研究问题和实验框架

**RQ-A（优先）**：在具备完整知识版本追踪和任务依赖缓存的强基线下，显式的证据类型、有效性约束和审计路径，能否降低历史修订后的错误复用率，并在安全约束下改善每个通过审核视频片段的综合成本？

**RQ-B（辅助）**：在固定模型、固定语料与预算的条件下，逐句断言引用与来源类别标注，能否减少生成内容中缺乏充分证据支持的历史叙述，同时维持可接受的拒答率、创作质量和审核负担？

**必测方案**：R0 全流程重跑、R1 检查点、R2 基础依赖缓存、R2+ 知识版本和依赖完整缓存、R3 证据感知有效性；R4 成本-质量策略单独作为探索。所有方案均需共同通过相同不变量测试。

**不能省的对照**：历史日期修改、史料被撤销、史实改为文学叙述、只修改字体、修改视频风格、视频API提交后崩溃、重复回调、跨用户工件混用、视频输出损坏、取消后延迟回调。至少报告错误复用、额外调用、成本、耗时、人工审核分钟数。模拟器与真实供应商分开报告。

**关键反证标准**：如 R3 对 R2+ 在真实编辑分布上无显著安全或成本收益，则将其定位为领域溯源工程实践，不制造原创算法的夸大叙述；后续另择更强的 Agentic Infrastructure 系统问题。

## 21. 终审意见

这份 Claude 报告可以作为**架构研究草案 v1**永久保留；其中 §1、§2、§7、§12、§14、§15 的总体思想可直接继承；§4、§6、§8、§9、§16 必须在真正开工前重写关键定义；§10、§13 应引入官方一手资料、真实兼容测试和更严格的实验基线。

**工程决策**：先修复已有系统、建设一条从史料到成片的可靠闭环，并在小规模模拟系统上做恢复机制对照；不要把 17 章一次性交给 AI 自治改代码。研究目标不是制造尽可能多的 Agent，而是证明可恢复、可解释、可核验的多模态系统在可重复实验中的实际收益。
